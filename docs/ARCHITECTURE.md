# Архитектура

## Общая схема

```
Источники (RSS/Atom, публичные витрины Telegram, YouTube RSS, HTML-листинги офиц. сайтов, GDELT)
   │  ingest-воркер: планировщик (next_poll_at, экспоненциальный backoff до 6 ч, здоровье источника),
   │  вежливый fetcher (robots.txt, ≥1 с между запросами к хосту, ETag/Last-Modified, лимит размера, свой UA)
   ▼
raw_item  ── оригинальный ответ как есть (хранится GEONEWS_RAW_RETENTION_DAYS)
   │  job (Postgres, SKIP LOCKED)
   ▼
process-воркер: чистые стадии, каждая пишет трассу в article_analysis
   normalize → text → language → date/time → geoparse (place resolution) → event type → category
   → dedup (URL, хэш, SimHash+Jaccard) → clustering (событие) → trust → пересчёт события
   ▼
article, article_location, event, event_article, event_rollup (триггер), event_change_log
   │  NOTIFY event_changes
   ▼
API (FastAPI): агрегаты карты, ленты, карточки, поиск, тайлы, SSE-broker (LISTEN) → браузер (MapLibre globe)
maintenance-воркер: фоновое слияние похожих событий, возврат зависших задач, очистка raw и журналов
```

## Слои (Clean Architecture)

| Слой | Пакеты | Правило |
|---|---|---|
| Домен | `domain/` (нормализация и леммы, таксономия мест, лексиконы, геоматематика) | без I/O; общий для газеттира и текста |
| Правила конвейера | `pipeline/` (геопарсинг, даты, категории, дедуп, кластеризация, доверие, сборка события) | чистые функции над данными; к БД обращаются только через порты (`GazetteerPort`) и репозитории |
| Инфраструктура | `db/` (пул, миграции, репозитории), `ingestion/`, `queue/`, `realtime/` | SQL без ORM, только в репозиториях и маршрутах |
| Входы | `api/`, `workers/`, `cli.py` | тонкие: разбор параметров, вызов стадий |

Геопарсер тестируется на фейковом газеттире и на реальной БД (golden-набор). Кластеризация и доверие —
чистые функции с unit-тестами.

## Решения (ADR)

**ADR-1. Глобус: MapLibre GL JS 6 с проекцией `globe`.** Один движок от планеты до улицы, open source,
векторные тайлы. Альтернативы и причины отказа — в RESEARCH.md §1. Воркер MapLibre собирается через
Vite `?worker&url` в самодостаточный файл: `?url` в проде теряет его общий чанк.

**ADR-2. Собственная подложка из PostGIS.** Полигоны стран (Natural Earth) и точки мест отдаются как MVT
(`ST_AsMVT`) с эндпоинта `/tiles/base/{z}/{x}/{y}.pbf`, глифы лежат локально. Карта работает без внешних
тайл-серверов. Рамка выборки расширяется в градусах *после* перевода в 4326, иначе тайлы у антимеридиана
выбирают противоположное полушарие. Кроме того, рамка ограничена широтами Web Mercator (±85,0511°), и геометрия
обрезается ею до трансформации: полюс в Mercator не переводится.

**ADR-3. Python + FastAPI + psycopg 3, без ORM.** Лучшая NLP-экосистема (pymorphy3, lingua, trafilatura,
feedparser, dateparser). Пространственные запросы выражаются прямо в SQL.

**ADR-4. PostgreSQL 16 + PostGIS 3.4 + pg_trgm — единственное хранилище.** В одной транзакционной БД
живут геоиндексы (GiST/KNN), GIN по массивам предков и триграммам, очередь (`SKIP LOCKED`) и шина
событий (`LISTEN/NOTIFY`). Новых сервисов для MVP не нужно.

**ADR-5. Газеттир — собственные таблицы, наполняемые из GeoNames.** Иерархия универсальна
(`kind`: continent / country / admin1..5 / locality / sublocality / street / point). Местный тип
(«станица», «хутор», «Gemeinde») — это данные (`local_type`), а не код. Никаких белых списков городов:
любой объект газеттира может стать местом события.

**ADR-6. Геолокация без LLM на правилах и газеттире** (решение пользователя). Прозрачна (каждое решение
объясняется в «Почему здесь?»), детерминирована и быстра: ~6 мс на документ. Не зависит от
NER-моделей, которые не знают хуторов.

**ADR-7. Очередь на Postgres.** Воркеры обращаются к ней только через `queue/pg_queue.py`. При росте
нагрузки её меняют на Redis Streams или Kafka, не трогая стадии конвейера.

**ADR-8. Realtime через SSE.** Поток односторонний. Подписка несёт фильтры и bbox. `Last-Event-ID` и
таблица `event_change_log` позволяют дочитать пропущенное после переподключения. Каждый процесс API
держит один `LISTEN` и сам раздаёт события своим подписчикам.

**ADR-9. Почасовой rollup для агрегатов карты.** Таблицу `event_rollup` (уровень × час × объект ×
категория × маска типов источников × live × own) ведёт триггер на `event`, поэтому любой путь записи
остаётся согласованным. Незавершённый первый час окна считается точно по `event`. Без rollup глобальные
агрегаты на 1 млн событий занимали секунды, с ним — десятки миллисекунд (см. VERIFICATION.md).

**ADR-10. Состояние интерфейса в URL.** Место, событие, фильтры и камера живут в URL, поэтому любой вид —
это ссылка. Роутер-библиотека не нужна.

**ADR-11. Исходные данные неизменны.** Сырой ответ лежит в `raw_item`, нормализованная статья — в `article`
(правки хранятся в `article_version`), результаты анализа — в `article_analysis` (стадия, метод, версия, JSON).
Анализ можно пересчитать, оригиналы при этом не трогаются. Дубликаты не удаляются, а связываются
(`duplicate_of`, `origin_group_id`).

## Масштабирование

- **Воркеры** `process` масштабируются горизонтально: задачи раздаются через `SKIP LOCKED`, привязка к
  событию сериализуется транзакционным advisory-lock'ом по региону (admin1): два воркера не создадут
  двойников одного пожара. Регионы между собой обрабатываются параллельно.
- **API** не хранит состояния, кроме кэша агрегатов. Кэш инвалидируется по последнему id журнала изменений.
  Запускается в несколько процессов за балансировщиком. Сейчас один процесс uvicorn даёт ~21 запрос/с
  на смешанной нагрузке на 4 общих ядрах.
- **Данные**: запросы к событиям идут по частичным индексам (`status = 'active'`) и по rollup. Следующие
  шаги при росте — дневной rollup для окна 7+ дней, секционирование `article` и `raw_item` по месяцам,
  реплики для чтения.
